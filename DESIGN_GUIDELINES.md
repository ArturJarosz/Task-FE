# App design guidelines (v2)

Rules every screen in this app follows. When building or changing UI, by hand or with Claude Code, read this file first. If a screen needs something not covered here, add the rule here first, then build it.

Stack: Angular 21, PrimeNG 21 (styled mode, `AppThemePreset` in `src/app/theme/app-theme-preset.ts`, based on Aura), Tailwind 4 with `tailwindcss-primeui`. The look follows the TailAdmin dashboard: Outfit font, a brand colour (default muted blue `#415cc8`, configurable), white 16px-rounded cards on a light grey page, and a dark theme (section 2, "Theming").

## 1. Principles

1. **Soft cards on grey.** A page is white cards (1px `gray-200` border, 16px radius, a soft `shadow-card` under them) on `gray-50`. Never nest cards in cards, accordions in cards, or tabs inside accordions.
2. **Brand colour means action or selection.** `brand-500` is for primary buttons, the active nav item, the active tab, links, and focus. Status uses its own colors (section 5). Everything else is grey.
3. **Say what a button does.** Buttons have text labels ("New project", "Add stage", "Save changes"). Icon-only buttons are allowed only for row actions (`⋯`), close buttons, top bar icons, field help (see "Field help"), the dashboard's "Customize dashboard" button and a submit button joined to its own one-field form (the task page's quick time entry, `pi-plus`), always with `aria-label` and a tooltip.
4. **Read first, edit on purpose.** Detail pages show values as text. Each section card has an "Edit" outline button that opens a dialog with the form.
5. **Tokens, not overrides.** Colors, radius, and spacing come from `app-theme-preset.ts` and the `@theme` block in `styles.css`. No `::ng-deep`, no hex values in components, no inline color styles. Use Tailwind classes such as `text-gray-500` and `bg-brand-50`, which match the tokens.
6. **Data is 400.** Regular weight is the default for showing data. Field values on detail pages (`.app-field-value`) and summary amounts are 400 too. A heavier weight needs a reason: the row's own name in a table (500), totals (600), figures in KPI cards and stat tiles (600–700) and titles (600). Everything a row or card only refers to (a client or architect in the Projects list, a date, an amount) stays 400.

### Typography (Outfit; body 16px)
Tailwind's `text-xs` / `text-sm` / `text-base` are redefined in `styles.css` as 14 / 16 / 18px, so use those classes rather than pixel sizes. Icons keep their own sizes (`text-xl` on `<i>`).
| Style | Size / weight | Use |
|---|---|---|
| Page title | 24px / 600 | `.app-page-title`, one per page; a step above the 20px card titles so it leads the page |
| Dialog title | 26px / 600 | Dialog headers |
| Card title | 20px / 600 | `.app-card-title` |
| KPI number | 24px / 700 (20px below `sm`, where the card is one line; 32px for a standalone figure such as the payments gauge) | `.app-kpi-value` (`.app-gauge-value`) |
| Body | 16px / 400 | Everything else, and all data: field values on detail pages (`.app-field-value`, `gray-800`), table data (dates, categories, counts, money), summary amounts |
| Row name | 16px / 500 | In tables only the row's own name (the project in Projects, the client in Clients, the cost in Costs). Other records a row refers to, such as the client and architect in Projects, are 400 like the rest of the data |
| Total | 16px / 600 | Total and balance rows (financial report, the dashboard's year summary) |
| Form label | 16px / 500, `gray-700` | `.app-form-label` |
| Table header | 16px / 500, `gray-500`, the size of the data under it | `<th>` (set globally in `styles.css`) |
| Field label | 14px / 400, `gray-500` | `.app-field-label` |

Money and counts use `.app-num` (tabular, right-aligned) and the PLN pipe: `{{ v | currency:'PLN':'symbol':'1.2-2' }}` renders "50 000,00 zł".
Time spent (whole minutes from the backend) uses `.app-num` too and the `duration` pipe (`src/app/shared/duration`): "12 h 30 min", "45 min", "3 h", and no time as "0 h". A figure in a narrow column (a card footer) uses the short format, `duration:'short'`: "12h 30m", the way time is typed in the Log time dialog.

### Shape and spacing
- Radius: 8px controls (every button with a fill or an outline, labelled or icon-only: never pills or circles), 12px icon tiles and menus, 16px cards, 24px dialogs, 8px for status tags (the same corner as buttons), full for avatars.
- Controls are 40px tall: inputs, selects, buttons, the segmented control frame (36px items plus 2px padding) and the calendar toolbar, so controls in one row always line up. The height is one token, `--spacing-control` in `styles.css` (`h-control`, and `h-control-inner` for items inside a segmented frame); the preset's padding adds up to it (24px line + 2 × 7px + 2px border). Icon-only buttons are 40×40. `size="small"` renders like the default size, so don't use it.
- Gaps: 16px between cards and grid columns of cards, the gutter (`gap-gutter`; the size is one token, `--spacing-gutter` in `styles.css`), 24px card padding (`p-6`), 20px vertical card header padding (`py-5`).
- Shadows: `shadow-card` under every card (`.app-card` has it; a card built without `.app-card`, such as the Payments card with its grey footer, adds it), `shadow-theme-xs` on inputs and outline buttons, `shadow-theme-xs` plus an even inner shadow on the active segment of a segmented control (`inset-shadow-pressed`: a 1px inner ring and a 3px soft inner shadow with no offset, so the segment still looks centred in its frame; `.app-seg-item.active` and the calendar's view switch), a soft inner shadow on the segmented control track (`inset-shadow-track`: 1px from the top plus a faint 1px inner edge, so the `gray-100` track shows on the `gray-50` page too; `.app-seg` and the calendar's button groups), plus a soft overlay shadow on dialogs and menus. Nothing else gets a shadow.
- Focus: a 2px `brand-500` ring with a 2px gap around the control (`focusRing` in the preset; custom elements use `shadow-focus-ring`, which draws the same ring), so keyboard focus is clearly visible (WCAG 2.4.7). Table rows and row links get it too. Inputs and selects show focus with a `brand-500` border instead.

### Theming (brand colour and dark mode)
Every colour is a CSS variable, and PrimeNG and Tailwind read the same ones, so components never need to know the theme.
- **Brand colour:** the "Theme color" system parameter (`#rrggbb`, one value for everyone), edited under Settings › Appearance. `ThemeService` turns it into the `--app-brand-50…950` scale plus `--app-brand-contrast` (white or `gray-900`, whichever reads better on `brand-500`) and writes them on `<html>`. The PrimeNG `primary` palette and Tailwind's `brand-*` both point at these variables. The default `#415cc8` (`DEFAULT_BRAND_COLOR`; the backend seeds the parameter with the same value) keeps the shades written in `styles.css`: PrimeNG's `palette()` output for it, except a stronger 10% tint for 50, because the generated one is almost white. Changing the default means changing the backend default, `DEFAULT_BRAND_COLOR` and those shades together.
- **Dark mode:** `<html class="app-dark">`, a per-user choice (Settings › Appearance), saved per user as the `THEME_MODE` user configuration (`USER_CONFIGURATION` table; `GET /users/current/configurations`, `PUT /users/current/configurations/THEME_MODE` with `LIGHT` or `DARK`). `localStorage` keeps a copy so the next start paints the right mode before the user loads; a user without an account record keeps the choice in the browser only. The `.app-dark` block in `styles.css` gives the same variables dark values: the grey scale runs the other way (`gray-50` is the darkest background, `gray-800` the light main text), `white` becomes the dark card surface, and `brand-50/100`, `success-50`, `warning-50` and `error-50` become dim tints, with their text shades lighter. PrimeNG's own dark scheme is off (`darkModeSelector: 'none'`); its light scheme follows the variables.
- **Rules:**
  - Use the token classes as usual (`bg-white`, `text-gray-800`, `bg-brand-50 text-brand-600`). They adapt by themselves, so don't add `dark:` variants.
  - `white` means "surface", not the colour white. For text on a brand fill use `var(--app-brand-contrast)`, and for a fill that must not change in dark mode use `--app-brand-500`.
  - For backdrops use `bg-black/40`, not a grey (greys flip).
  - Charts read colours with `cssColor()` when they build their data, so they pick up the theme of the moment they render.
  - No new hex values in the preset or components: add a variable in `styles.css` with a light and a dark value.

## 3. App shell

- **Sidebar** (`--app-sidebar-w`, 290px): white, right border `gray-200`. The logo sits at the top. Groups are labelled in uppercase 12px `gray-500`: *Work* (Dashboard, Projects, Calendar), *People* (Architects, Clients, Contractors, Suppliers), *Finance* (Financial report), *Admin* (Settings).
  - Items: `.app-nav-item`, 14px medium `gray-700`, 8px radius, hover `gray-100`. They are 44px tall (`min-h-11`, collapsed too), not the control height.
  - Active item: `.app-nav-item.active`, with `brand-50` background, `brand-600` text (`brand-500` text is 3.7:1 there in the dark theme) and a `brand-500` icon, and `aria-current="page"` (`ariaCurrentWhenActive="page"`).
  - Collapsed (from `lg`, the top bar's menu button): 90px wide, icons only, the logo clipped to its round mark, each group label replaced by a `gray-400` `⋯`, and item labels as tooltips on the right. Collapsing and expanding animate in place over 300ms (`ease-in-out`) and nothing jumps: the width shrinks, labels fade out at once (150ms) and get clipped (never wrapped or hidden), the icons slide to the middle, and the `⋯` fades in last. Expanding runs it the other way, with the labels fading in only once the sidebar has grown (100ms delay). With reduced motion it switches at once (`motion-reduce:transition-none`).
  - Icons are PrimeIcons only (remove `font-awesome`):

    | Item | Icon |
    |---|---|
    | Dashboard | `pi-th-large` |
    | Projects | `pi-folder` |
    | Calendar | `pi-calendar` |
    | Architects | `pi-id-card` |
    | Clients | `pi-users` |
    | Contractors | `pi-wrench` |
    | Suppliers | `pi-truck` |
    | Financial report | `pi-chart-bar` |
    | Settings | `pi-cog` |
- **Top bar** (76px): white with a bottom border. It holds a search field (40px, "Search or type command...", ⌘K hint) on the left, and on the right a round 40px notifications button plus the user avatar, on its own. The avatar opens the user menu; its tooltip shows the user's name and its `aria-label` adds what it does ("Maria Kowalska, open account menu").
  - **User menu:** a `p-menu` popup, 256px wide and right-aligned under the avatar. Its `start` template shows the avatar, name and email over a `gray-200` divider; the items below are actions only (today just "Log out" with `pi-sign-out`). Never show information as a disabled menu item.
- **Menus** (user menu, row `⋯` menus): 12px radius, 8px list padding, 14px `gray-700` items with `gray-500` icons and a `gray-100` hover. These come from the `menu` tokens in the preset.
- **Content:** 24px padding, max width 1536px.

## 4. Page templates

### Every page
`.app-page-header`: page title on the left, breadcrumb on the right (Home › Projects › Lublin 01). It is at least one control high (40px, `min-h-control`) with everything centred, so a page with header buttons (the dashboard) starts its first card at the same height as every other page.
Use `<app-page-header title="Project" [crumbs]="crumbs"/>` (`src/app/shared/page-header`) and set `data: {ownPageHeader: true}` on the page's route so the app shell hides its old breadcrumb bar. The page header also names the browser tab: the last breadcrumb, then the app name ("Dom w Zielonej Górze · OMCD", "Projects · OMCD"), so tabs and history entries can be told apart and screen readers announce the page. Page-wide actions (only the dashboard has any today) go inside it as content and sit right of the breadcrumb. Read-only fields use `<app-field label="…" [value]="…"/>` (`src/app/shared/field`), which shows "Not set" (or `emptyText`) when empty.

### Card rows (every page)
A row of cards is either one full-width card, or cards whose widths are 25%, 50% or 75%. Never `auto-fit`, never fixed sidebar widths such as 340px, and never three equal cards. Below `xl` (1280px) every card is full width and the rows stack. From `xl` the row is a 4-column grid:
- Four KPI cards: `grid grid-cols-1 md:grid-cols-2 xl:grid-cols-4 gap-gutter`. Each card is 50% from `md` and 25% from `xl`. Below `sm` a KPI card is one compact line (no icon tile, label on the left, figure on the right, `px-4 py-3`), so a row of four takes about a quarter of a phone screen, not all of it. `<app-kpi-card>` does this itself.
- Two cards at 50%: `grid grid-cols-1 md:grid-cols-2 gap-gutter`. Not for KPI cards: two short figures in half-width cards leave each card mostly empty, so a list page shows four KPIs (Clients: Clients, With active projects, Companies, Contract value; Architects: Architects, With active projects, Active projects, Contract value; Contractors and Suppliers: the count, With jobs / With supplies, Jobs / Supplies, Trades / Shop types in use).
- Main and side column at 75% / 25%: `grid grid-cols-1 xl:grid-cols-[calc(75%_-_var(--spacing-gutter)/4)_minmax(0,1fr)] gap-gutter`. Taking a quarter of the gutter off the 75% lines the side column up with the fourth card of the KPI row above.
- Three cards: `grid grid-cols-1 xl:grid-cols-4 gap-gutter`, with the widest card `xl:col-span-2` (25 / 25 / 50).
- Five KPI cards (only the project Finance tab): `grid grid-cols-1 md:grid-cols-2 xl:grid-cols-4 2xl:grid-cols-5 gap-gutter`, the fifth card `md:col-span-2 xl:col-span-4 2xl:col-span-1`. The first four keep the four-card row and the fifth gets a full-width row of its own, until all five fit in one row from `2xl`, where each card is about as wide as a 25% card at `xl`.
- A card in the 25% side column can be as narrow as about 230px (just above `xl`). Its content must fit that: a gauge or chart shrinks with the card (`w-full max-w-[…]`), and a row of figures uses the card figures footer below.
- Card figures footer (Payments, Time and rate): a grey footer with a few figures, built with `.app-card-figures` on the `<dl>`, `.app-card-figure` on each item and `.app-card-figure-label` / `.app-card-figure-value` on its `dt` / `dd`, in a card with the `@container` class. From 19rem of card width the figures sit side by side, centred, with a `gray-200` line between them; below that each takes a row, label on the left and value on the right, with a line between rows, so values never overflow.

### Dashboard
Each user arranges their own dashboard out of widgets, in rows of **stacks**. A stack is a column of up to three widgets on top of each other; it is 25%, 50%, 75% or 100% wide, never narrower than the minimum of any widget in it, and the stacks of a row add up to at most 100%. A row is as tall as its tallest stack, and the widgets of a stack split its height equally (minus the gutter); when their content needs more, the row grows instead, so a chart at 50% next to a stack of Year summary and Upcoming events gives each of those half the chart's height. Every card stretches to the height it gets. The layout is saved per user as the `DASHBOARD_LAYOUT` user configuration (`PUT /users/current/configurations/DASHBOARD_LAYOUT`, a versioned JSON document the frontend owns, at most 4000 characters; version 2 has stacks, version 1 layouts are read as one stack per widget). Until a user saves one they see the default layout, one widget per stack: A widget whose content is shorter than the height it gets (an empty Upcoming events list) centres its empty state in the card instead of leaving a blank area under it.
1. A row of four KPI cards (see Card rows). Each is an `<app-kpi-card icon="pi pi-…" label="…" [loading] [loadFailed]>` (`src/app/shared/kpi-card`), the same card the list pages use: a 48px grey icon tile on the left, then the label above a 24px number (the projected content), plus optional context after the number in `.app-kpi-context` (14px regular `gray-500` text on the number's baseline: "on 2 tasks", "of 9", "175 days ago"). Context is plain text, never a tag (see Status tags). It shows the skeleton and "Couldn't load" itself.
2. A chart card (title, subtitle, segmented Monthly / Quarterly / Annually) at 75% next to a summary card at 25%. The summary lists income, expenses and the balance, and ends with the "Open financial report" button at the bottom of the card. No ratios such as expenses as a share of income: the app manages design projects, it isn't a finance tool.
3. A list card ("Upcoming events") next to a table card ("Active projects"), 50% each. Each shows at most 5 rows and has a "See all" outline button that opens the full page.

Widgets (`DASHBOARD_WIDGETS` in `src/app/dashboard/layout/dashboard-layout.ts`; each can be placed once): Active projects count, Income / Expenses / Balance this year (KPI cards), Income and expenses chart (at least 50%; Annually covers the last 5 years), Year summary, Upcoming events, Active projects table (at least 50%). A new widget gets a definition there, a case in the dashboard's widget template, and a minimum width if it is a chart or table.

Rows follow Card rows, with stacks in place of cards: from `xl` a row is a 4-column grid and a stack spans its width. Between `md` and `xl` a row is 2 columns: in a row of only 25% and 50% stacks each takes one column (a last odd one spans both), in any other row every stack is full width. Below `md` every stack is full width. The widgets of a stack always stay on top of each other.

**Edit mode.** An outline icon button (`pi-sliders-h`, "Customize dashboard") right of the breadcrumb switches to edit mode; there the header shows a text "Reset to default", an outline "Cancel" and the primary "Save layout" instead. Saving leaves edit mode with a "Dashboard saved" toast; a failed save keeps edit mode and the draft. Leaving the page drops unsaved changes. In edit mode:
- A grey hint line says how to move stacks and widgets.
- Each row is a dashed `gray-300` 16px-rounded area (not a card) with "Row N", "N% free" and a `⋯` menu (Move row up, Move row down, Remove row).
- Each stack is a `gray-100` 16px-rounded panel. Its top bar is a `pi-arrows-alt` grip, a segmented width control (on a `gray-200` track; widths that don't fit are disabled) and a `⋯` menu (Move left, Move right, Move to row above, Move to row below, Remove stack, or Remove widget for a stack of one). Dragging the bar moves the stack within its row or into any row with room for it, where it narrows to the free space.
- Each widget in a stack has a bar above it: a grip, the widget name and a `⋯` menu (Move up and Move down within a stack of several, Move into stack on the left / right, Move out of stack, Remove widget). Dragging the bar moves the widget within its stack or into another stack with fewer than three widgets that is wide enough for it; a stack it leaves empty disappears. "Move out of stack" puts it in a new stack right after, taking the row's free space first and then narrowing the stack it leaves. The widget itself shows as in view mode but `inert`.
- The free part of a row (at least 25%) is a dashed `.app-add-tile` area. Dropping a widget there gives it a stack of its own. While some widget not on the dashboard fits there, it is an "Add widget" button that opens a dialog listing those widgets (icon tile, name, one line, the width it will get, or "Needs N% free" disabled); picking one adds it as a new stack. Otherwise it says "Drop a widget here to give it its own stack".
- A full-width dashed "Add row" tile ends the page.
- An empty saved dashboard shows one card with an empty state and an outline "Customize dashboard" button.

The dashboard keeps its own `DashboardStore`, so it never changes the financial report page's filters; it also holds the layout being edited.

### List page (Projects, Clients…)
1. Optional row of `<app-kpi-card>`s.
2. One card holding the table. Its header has the title and subtitle on the left; on the right sit a status segmented filter, a "Filter" outline button, and the primary "New project" button.
3. The table header band is `gray-100` with a `gray-200` line under it, and a short (20px) `gray-300` line between column headers. All of it is global (the preset and `styles.css`) and applies to every header band: PrimeNG tables, the div tables of the Settings page (their header row is `.app-table-head`, which draws the line in the middle of the `gap-3` between its cells) and the calendar's day names. Group rows inside a table (the financial report's Income / Expenses) use the same `gray-100`. Rows have a checkbox and a two-line name (name in 500 `gray-800`, type in 12px `gray-500`). People appear as initials avatars plus name and role. Avatars (`.app-avatar`) use the status tags' colours and fill (their tint with 8% of the text colour over it, like `tagFill()`): `bg-brand-50 text-brand-600` for architects and the user, `bg-warning-50 text-warning-700` for clients, `bg-gray-100 text-gray-700` for partners. Rows show them, followed by status tags, money right-aligned (400, like all table data except the row's own name), and a `⋯` row menu. Table cells are 16px through a rule in `styles.css` (in the `components` layer, so a `text-*` class on a `<td>` still wins).
4. The footer has "Showing 1–10 of N" plus Previous and Next buttons (`<app-table-footer>`). The buttons show only when there is more than one page.
5. **Row links.** The row's own name is a real link (`<a class="app-row-link">`), so Ctrl or middle click opens it in a new tab and screen readers announce it as a link; it stops the click from reaching the row. The whole row stays clickable with the mouse, but the `<tr>` gets `tabindex="-1"`, so the keyboard goes to the link only. Rows end with a `⋯` menu when they have actions and with nothing otherwise (no chevrons).
6. **Initials.** Avatars show the first letters of the first two words that start with a letter or digit (`initials()` in `label-utils.ts`): "Teodor Czerwiński" is "TC", "Ciuba & Partnerzy" is "CP", "IISKELO" is "I". Never write another initials helper.
7. **Sorting.** Every column of a list page table except the row menu sorts (`pSortableColumn` with a `<p-sortIcon>`, the only spelling PrimeNG 21 accepts). The table is `[lazy]="true"` and emits the sort; the shell sorts all filtered rows before it pages them (`sortRows()` in `src/app/shared/utils/sort-utils.ts`), so sorting covers every page and goes back to page 1. Text sorts the Polish way, missing values last. Every other table sorts too (stages, tasks, finance components, a partner's items, a client's or architect's projects): it is `[lazy]="true"` as well and shows `rows | sortRows:sort:sortValue` (`SortRowsPipe` in `src/app/shared/sort-rows`), so the input array, often frozen store state, is never sorted in place. Columns that show a label (status, category, a person) sort by that label through the component's `sortValue`. The stage list starts in time order.
8. **Below 640px** a table shows only its first column and the row menu: the other cells are `max-sm:hidden`, and the first cell adds the status tag (when the row has one) under the name with `sm:hidden`. The table's minimum width applies from `sm` only (`tableStyleClass="sm:min-w-…"`), so it never scrolls sideways on a phone. Finance component tables (costs, supplies, contractor jobs, installments, supervision visits, a partner's items) show their first column and the money (`styleClass="app-table-phone"`, which hides every other column without `.app-num` below 40rem), so they don't scroll sideways either. Segmented controls that must stay on one line (routed tabs, chart period switches) use `.app-seg-tabs`; where even that doesn't fit a phone (the five Financial components, the Settings sections), a `p-select` with the same options replaces them below `sm`.
9. Columns that only hold a short figure (counts) are narrow (`w-32`) and the contact column of the partner lists is 22rem wide, so the name column takes the free width and the figures sit next to the data they belong to instead of across a gap.

### Projects page views (`/projects`, `/projects?view=timeline`)
The Projects card shows the same projects two ways. A segmented view switch (`.app-seg`, "Table" with `pi-list` and "Timeline" with `pi-align-left`) is the first control on the right of the card header, before the status filter; the view is the `view` query parameter (none for the table), so the browser's Back button and a shared link keep it. Both views share the status filter, the "Filter" popover and the page index (switching views goes back to page 1); the KPI row above always counts every project.

**Filter.** An outline "Filter" button (`pi-filter`; "Filter · N" while N filters are on; `min-w-30`, as wide as "Filter · 9", and the status counts `min-w-[2ch]`, so the header controls never move as filters change) opens a `p-popover` (about 560px) with a 2-column form: Search (project name), Period (`p-datepicker selectionMode="range" view="month"`, "mm.yyyy"; keeps projects with any date in those months), Client, Architect (`p-select` with `[filter]="true"` and `[showClear]="true"`, options from the loaded projects), Project type and Contract status (`p-multiselect`), and a "Past deadline only" `p-toggleswitch` (a contract whose bar is past its deadline, see the project timeline). Filters apply as they change; a text "Clear filters" button ends the form. While filters are on, a line under the card header lists each as a removable `p-chip` ("Client: Jan Kowalski", "Period: 06.2026 – 03.2027") and ends with a text "Clear filters" button. With no matches the card shows the empty state "No projects match these filters" with an outline "Clear filters" button.

**Loading.** Until the projects load, both views show skeletons in the card; a failed load shows `<app-empty-state>` with `pi-exclamation-triangle`, "Couldn't load projects" and an outline "Try again", never an empty list. A failed reload with projects already on screen keeps them (the error toast says it failed). The date filters and the timeline use today and move on at midnight.

**Timeline view.** The card title is "Projects timeline", with no subtitle (the rows and the month axis say what is drawn). A pasted key is checked in the browser (a JSON key with `type: service_account`), and a key for a different service account gets a warning hint, because saving it moves sync to a new calendar. "Save changes" sends only the changed parameters through `PUT /system-parameters/{id}`, key first and sync last. If a save stops at an error, the fields that were stored show the stored value and the rest keep what was typed; "Cancel" and the primary "Save changes" sit at the bottom right. While the connection is "Connected", a "People with access" block follows in the same card (`GET/POST/DELETE /calendars/shares`): one row per person with the email, a role `p-tag` ("Can view", "Can edit", "Free/busy only", "Owner") and a small text secondary "Revoke" button that opens the page's confirm dialog (a `danger` "Revoke" accept, because it removes access). Roles the application cannot give (owner, free/busy) show "Managed in Google" instead of "Revoke". Below the list sit an email input, a "Can view"/"Can edit" `p-select` and an outline "Share" button (outline, because "Save changes" is the card's primary); an email that already has access gets an inline error. Skeletons show only before the first load; later connection checks refresh the list in place.

### Signed-out pages (`/not-logged-in`, `/logout`)
Render inside the app shell with `data: {ownPageHeader: true}` on the route and no page header or breadcrumb. The top bar shows only the sidebar toggle, because search, notifications and the user menu need a signed-in user. One centered card (`max-w-lg`, `mt-12`, `p-8` at every width, text centered) with a 56px grey icon tile, the page title, one line of explanation, and a live countdown to the redirect, "Redirecting to the login page in 3 s…" (`aria-live="polite"`). The only button is primary and starts login at once; the redirect still happens after the countdown. Copy says "log in" and "logged out", never "sign in" or "signed out".

## 5. Components

### Buttons
| Type | PrimeNG | Use |
|---|---|---|
| Primary | `<p-button label="New project" icon="pi pi-plus" />` | The main action. At most one per card or dialog. |
| Outline | `severity="secondary" [outlined]="true"`: `brand-300` border, `brand-600` text, `shadow-theme-xs`, `brand-50` hover (preset `button.colorScheme.light.outlined.secondary`; the calendar's "Today" copies it in `styles.css`) | Filter, Export, Cancel, See all |
| Edit | outline + `icon="pi pi-pencil"` | Section card "Edit" |
| Danger | `severity="danger"` | Only inside delete confirmations |
| Row action | `icon="pi pi-ellipsis-h" [text]="true" [rounded]="true" severity="secondary"` + `pTooltip` | Table rows |
| Field help | `icon="pi pi-question-circle" [text]="true" [rounded]="true" severity="secondary"` + `ariaLabel` | Next to a field label whose value has to be fetched elsewhere |

Shape: every button with a fill or an outline (primary, outline, Edit, danger, and icon-only ones such as the header `⋯`, the sidebar toggle and "Customize dashboard") has the 8px control radius, so buttons in a row look alike. `[rounded]="true"` is only for icon-only `[text]="true"` buttons (row actions, field help, inline row edit and reset), whose hover fill is a circle. Never use `size="small"`.

### Field help
When filling a field needs steps outside the app (such as the Google Calendar service account key), put a help button right after its label. Its `pTooltip` is an `ng-template` with a short numbered guide: `tooltipEvent="both"` so keyboard focus opens it too, `[autoHide]="false"` so it stays open while the pointer is on it and its links can be clicked, `tooltipPosition="bottom"` and `tooltipStyleClass="max-w-md"`. Inside, use 14px text, a one-line title with `.app-tooltip-title` (bold, with the line under it, as on chart tooltips), at most six steps naming the exact menu path ("IAM & Admin › Service accounts"), underlined links that open in a new tab, and no colour classes (the tooltip has its own dark surface). Keep the hint under the field for the one-line explanation; the guide is for the how-to.

### Status tags (`p-tag`)
Tags with 8px corners (`border.radius.md` in the preset, the same corner as buttons) and a fill that is the light tint with 8% of their own text colour mixed in (`tagFill()` in the preset), so they stand out on white cards. 8% is the limit: green and amber text are at 4.6:1 on it, and a darker fill would drop them below 4.5:1. A tag shows a state: a status, Paid / Not paid, a project end that is "Before start". A count, a total, a distance in time or "ongoing" next to a figure is context, written as plain `gray-500` text (`.app-kpi-context` in a KPI card), never as a tag. Use them, always through `statusSeverity()` in `src/app/shared/status-severity.ts`:

| Status (backend enum value) | Severity | Look |
|---|---|---|
| Offer (`OFFER`) | `secondary` | grey |
| To do (`TO_DO`), Accepted (`ACCEPTED`), Signed (`SIGNED`) | `info` | blue |
| In progress (`IN_PROGRESS`), Pending / Delete pending sync (`PENDING`, `DELETE_PENDING`) | `warn` | orange |
| Done (`DONE`), Completed (`COMPLETED`), Synced (`SYNCED`) | `success` | green |
| Rejected (`REJECTED`), Terminated (`TERMINATED`) | `danger` | red |
| Google Calendar connection: Off / Not configured (`DISABLED`, `NOT_CONFIGURED`) | `secondary` | grey |
| Google Calendar connection: Connected (`CONNECTED`) | `success` | green |
| Google Calendar connection: Invalid key, No access, Calendar missing, Unreachable (`INVALID_CREDENTIALS`, `PERMISSION_DENIED`, `CALENDAR_NOT_FOUND`, `CONNECTION_FAILED`) | `danger` | red |
| Google Calendar share role: Can view (`READER`) | `info` | blue |
| Google Calendar share role: Can edit (`WRITER`) | `success` | green |
| Google Calendar share role: Free/busy only (`FREE_BUSY_READER`) | `secondary` | grey |
| Google Calendar share role: Owner (`OWNER`) | `warn` | orange |
| Release note type: New (`NEW`) | `info` | blue |
| Release note type: Improved (`IMPROVED`) | `success` | green |
| Release note type: Fixed (`FIXED`) | `warn` | orange |
| Finance item paid state (not a backend enum, so `paidSeverity()`): Paid / Not paid | `success` / `secondary` | green / grey |

The keys come from the generated enums (`ProjectStatus`, `StageStatus`, `TaskStatus`, `ContractStatus`, `CalendarEventSyncStatus`, `GoogleCalendarConnectionStatus`, `CalendarShareRole`). A new enum value fails to compile until it gets a severity in `status-severity.ts`. Labels come from the configuration entries via `resolveLabel()`. `contrast` (dark) is reserved for statuses that don't exist yet, such as "On hold".

When an entity has two statuses, label them explicitly: "Contract status" and "Project status".

### Charts
Every chart (the Chart.js bar charts on the dashboard and the financial report, and the HTML timeline on a project) looks like one system:
- **Card:** the card header has the title, a subtitle only for what the chart can't show itself (gross or net and the period: "Gross values, 2026"; never the date range already in the filters or what the legend says), and the legend on the right: a `list-none` `<ul aria-label="Legend">` in `text-sm` (16px) `gray-700`, `gap-x-5 gap-y-2`, whose items are a 10px swatch and the label (`flex items-center gap-2`). When the header's right side holds a control (the dashboard chart's Monthly / Quarterly / Annually switch), the legend is the first line of the card body instead (`mb-4`), above the plot. The current period of every chart is highlighted (today's date in Warsaw, like the backend's periods), and it moves on at midnight (`updateAtMidnight()` in `date-utils.ts`, which also catches up when the tab is shown again after the computer slept). The plot sits inside the card padding (`px-6 pb-6`); a chart that scrolls sideways scrolls inside that padding.
- **Axis labels:** `text-xs` (14px), regular weight, `gray-500`. Months with a year are "May'26" (and quarters "Q2'26"); the current period is labelled in the `today` colour at 500 weight.
- **Grid:** `gray-100` lines across the value axis only (horizontal on a bar chart, the month lines on the timeline), no axis lines, no grey header band. A `gray-200` line may separate groups of rows.
- **Bars:** 24px thick at most, 4px rounded at the data end (`rounded` on the timeline), and a 2px surface gap between touching parts (stacked segments, the on-time and past-deadline parts of a timeline bar). Chart.js draws that gap as a border inside the bar, so the outermost segment gets none, or it covers the rounding. Income and expenses of a period are two bars side by side, both up from zero, even when the backend sends expenses negative (every chart reads an expense through `expenseAmount()` in `chart-utils.ts`): plain bars on the dashboard, a stack per group (`stack: 'income'` / `'expense'`) of its categories on the financial report. Segments are shaped by their sign, so a negative value (a correction) goes below zero with its rounding at the bottom, and its tooltip shows it negative; `stackedSegmentShapes()` gives every stacked chart its gaps and rounding. An expense that isn't zero is drawn at least 3px tall (`minBarLength`, with zeros left out as `null`): both bars on the dashboard, the expense stack on the financial report (stretching a thin income segment would push it into the one above), so small expenses next to large income still show.
- **Series colours:** `--color-chart-1` to `--color-chart-6` in `styles.css`, used in that order. Neighbouring hues must stay apart: the sixth is a pink (`#d6409f`), not a violet, which read as the brand blue next to it.
- **Tooltip:** one dark surface for both kinds: `gray-800` with `white` text (these flip in dark mode), 12px padding, 8px radius, no shadow, `text-xs` text, a 600-weight title, and a colour dot before the line that belongs to a series. A title is set apart from the lines under it by a 1px line in the text colour at 25% opacity, 6px below the title and 6px above the first line (`.app-tooltip-title` on an HTML tooltip's title; Chart.js tooltips draw it with the `tooltipTitleDivider` plugin in `chart-tooltip.ts`). A tooltip of one line has no title and no line. Chart.js gets it from `barChartOptions()`; a `pTooltip` on a chart gets it with `tooltipStyleClass="app-chart-tooltip"` (in `styles.css`).
- **Empty:** `<app-empty-state icon="pi pi-chart-bar">` inside the card.

### Forms
- `.app-form-label` above the input, in sentence case with no colon. Required fields get a red `*`.
- Inputs fill their cell (`class="w-full"` on native inputs, `[fluid]="true"` on `p-select`, `p-datepicker` and `p-inputnumber`). Money uses `p-inputnumber` with a "zł" suffix. Dates use `p-datepicker dateFormat="dd.mm.yy" [showIcon]="true" appendTo="body"`. Always set `appendTo="body"` on date pickers and selects: otherwise the popup is clipped by the card or accordion it sits in.
- Errors show a light-red border plus a 12px red message under the field that says what to fix ("End date must be after the start date"). The placeholder of an invalid field stays `gray-400`, so it never looks like a typed value.
- A select whose value the app can't guess starts empty with a "Select a …" placeholder and gets "Select a …" as its error once left empty: the type, client and architect of a new project, like the stage, task and category pickers. Never preselect the first option.
- Save and Create buttons are never disabled because of errors. An edit dialog disables Save only while nothing has changed (and while saving); a new-item dialog never disables it. Saving with something missing calls `showErrors(form)` (`src/app/shared/utils/form-utils.ts`), which marks every field touched and dirty so each shows its own message, and stops. A disabled button would not say what is missing.
- Hints show as a 12px `gray-500` line under the field.
- Yes/no fields use `<p-toggleswitch inputId="…">` with its label to the right on the same row (14px medium `gray-700`). A toggle that reveals more fields ("Add an installment") gets a one-line hint under its label. On detail pages, show them read-only as "Yes" / "No" with `<app-field>`. In dialogs, put toggles together in one grid row, one toggle per column cell (`flex items-center gap-3`), so each lines up with the column below it. Place a toggle directly above the field it controls ("Paid" above "Payment date"). Never mix toggles and inputs in the same row, and never squeeze toggles into one cell.
- Person pickers (architect, client) are `p-select` with `[filter]="true"`, options labelled with the full name, and a hint when they default to a value ("Defaults to the project's architect").

### Empty states
Inside the card: a 56px grey circle with an icon, a 16px/600 title ("No stages yet", a `<p>`, not a heading, so it never skips a heading level under the card title), a line of explanation only when it adds something the title doesn't (how to start, or why it is empty: "Split the project into stages to plan tasks and installments"; not "Add the costs of this project" next to an "Add cost" button), and, when not already in the card header, the create button. `text` on `<app-empty-state>` is optional.

### Empty values
A missing value in a table cell, list or card is `<app-not-set/>`: "Not set" in `gray-500`, regular weight even inside bold cells. Read-only fields on detail pages use `<app-field>`, which shows the same. Yes/no table columns are `<app-yes-no-mark [value]="cost.paid" label="Paid"/>`: a green check for yes and a `gray-500` dash for no, announced as "Paid: yes" / "Paid: no". Never copy the markup into a template.

### Feedback
- A toast after save or delete: "Contract saved".
- An error toast is one plain-language line for people, never a URL, response code or id: the title says what failed ("Couldn't load stage", from the service's title through `toastTitle()`) and the line says what happened or what to do (`toastDetail()`: "Check your connection and try again.", "It may have been deleted.", the backend's own message for a request it rejected). A lost connection shows one "Couldn't reach the server" toast, however many requests failed with it. Both are in `src/app/shared/rest/abstract-rest.service.ts`.
- `p-confirmdialog` for destructive actions: "Delete Lublin 01? This can't be undone." Each page renders one `<p-confirmdialog [style]="{width: '480px'}" [breakpoints]="{'640px': '95vw'}"/>` in its shell; components nested in it (lists, cards) never add their own, or the dialog opens twice. Accept buttons say what happens ("Delete", "Reject stage", "Reopen stage") next to an outline "Cancel"; only deletes use `severity: 'danger'`.
- `p-skeleton` while loading, shaped like the content.
- When a load fails, replace the skeletons with an error state: `<app-load-error>` for a whole page ("Couldn't load this stage", an outline "Back to stages" and "Try again"), or `<app-empty-state>` with a warning icon and an outline "Try again" inside a single card. KPI values show "Couldn't load" in `gray-500`. The REST error toast still appears as well.

## 6. Copy
- Sentence case: "Financial components", "Edit contract".
- No descriptions that state the obvious (the same rule as in `AGENTS.md`). A card subtitle, dialog description, settings line or empty-state line must tell users something the title, labels, tabs and data don't already say: a filter or order ("To do and in progress, most recently changed first"), a time window ("Next 90 days"), gross or net, a consequence ("The new value is used from the next calculation on"). Otherwise leave it out.
- One word per thing everywhere: a client is "Private" or "Company" (never "Corporate", `clientTypeLabel()` in `src/app/client/model/client.ts`); chart periods are "Monthly / Quarterly / Annually"; the tax rates are "VAT rate" and "Income tax rate". Item amounts in the finance components (costs, supplies, contractor jobs, installments, supervision) are net, so their columns, fields and inputs say "Net value", never just "Value", next to the gross and net totals.
- Use "Net", never "Nett". Money is PLN, Polish format. Dates are `dd.mm.yyyy`.
- Name sections from the page's point of view: "Projects" on an architect page, not "Client projects".
